## Database

- Schema lives in TypeScript (`src/db/schema.ts`). Migrations are SQL files generated by `drizzle-kit generate` and **committed**. Never edit a migration that is already merged; add a new one.
- Each developer has a local, disposable database file configured in `.env.local` (`DATABASE_URL=file:./data/dev.db`). The `data/` folder is git-ignored. To reset: delete the file, then migrate and seed.
- The libSQL client accepts a local `file:` URL in development and a remote `libsql://` URL (e.g. Turso) in production, with the same code. The final deployment target is still open (see `docs/PRODUCT.md`).
- Tests use an in-memory database.
- SQLite does not enforce foreign keys unless `PRAGMA foreign_keys = ON` is set on each connection. The DB module must do it.
- Dates and booleans are stored as integers or text and converted by Drizzle; JSON columns are validated with Zod on read.
- Our data is a rebuildable copy of external sources: it can be recreated by running the sync.
- Two branches that both change the schema will produce conflicting migrations. Keep schema changes small, merge them quickly, and regenerate the migration after rebasing if a conflict occurs.

## Architecture rules

- The website and API routes **read only from our database**. Only the sync process talks to external providers.
- One adapter per provider in `src/adapters/`. Adapters validate raw responses with Zod and return the normalized shapes from `docs/DATA_MODEL.md`. They do not touch the database.
- All timestamps are UTC in storage; convert to the viewer's time zone only in the UI.
- Provider IDs are stored in `ExternalRef`, never in the main tables.
- Sport-specific logic stays behind the common model; do not leak provider response shapes into the UI.

## Git workflow

- Default branch is `master`. Never commit to it directly; all changes go through a pull request reviewed by the other developer.
- Branch names follow [Conventional Branch](https://conventional-branch.github.io/): `feature/`, `bugfix/`, `hotfix/`, `release/`, `chore/` followed by a short kebab-case description, e.g. `feature/team-ics-feed`.
- Commit messages follow [Conventional Commits](https://www.conventionalcommits.org/): `feat:`, `fix:`, `docs:`, `chore:`, `test:`, `refactor:`.
- Keep commits and PRs small and focused on one user story.
- Do not commit, push, or open PRs unless asked.

## Working rules

- For non-trivial work, propose a plan and wait for approval before writing code.
- New behavior comes with tests. Adapters are tested with saved response fixtures, never live network calls.
- Run lint, typecheck and tests before declaring work done, and report honestly if something fails or was not run.
- Never put secrets in code or commit `.env` files. Use `.env.local` (git-ignored) and keep `.env.example` up to date.
- Explain non-obvious code and decisions briefly; the developers are using this project to learn.
- Do not add dependencies without saying why.
- When docs and code disagree, point it out and update the docs in the same change.
